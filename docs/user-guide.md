# TrialLens — Detailed workflow and operations guide

Local AI courtroom simulation and legal decision-support workspace.

This guide preserves the existing operational documentation during the TrialLens rebrand. The current app still displays Judge & Jury and TrialForge in places. Return to the [project overview](../README.md).

## What It Does

- Creates local matters with pasted case narratives and Ontario/Canada jurisdiction defaults.
- Uploads evidence files, preserves the originals with SHA-256 provenance, and assigns immutable exhibit IDs like `E-001`.
- Accepts uploads up to 250MB by default, using disk-backed temp files instead of memory buffering.
- Runs structured courtroom rounds in realistic order: intake, issue spotting, Crown/plaintiff opening (the burden-bearer presents first), defence response, Crown reply, defence closing, the judge's charge to the jury, jury deliberation, and judge synthesis.
- Runs Ontario courtroom rehearsals in TrialForge, preserving every transcript, letting users reopen earlier sessions, and linking transcript citations to exhibit details and transparently labelled curated legal-authority sources.
- Tracks every simulation stage durably so failed runs can resume from the first incomplete stage, and recovers sessions orphaned by a server restart.
- Searches locally extracted evidence chunks so agents receive targeted exhibit context before each stage.
- Stores matters, evidence provenance and extracted text, turns, jury opinions, and verdict reports in local SQLite, with versioned migrations and consistent backups.
- Uses a real local OpenAI-compatible provider by default, such as Ollama, and can be explicitly configured for external MiniMax calls.
- Adds a Trial Engine v2 guided workflow: recursive folder/ZIP intake, neutral case-model approval, private competing theories, disclosure review, approved motions, versioned admission rulings, full proceedings, per-issue decisions, and scenario robustness runs.

This is decision-support software only. It is not legal advice and does not produce binding court outcomes.

## Guided case workspace

The default workspace has four destinations:

1. **Overview** shows the next preparation step and the case details. Use **Save case details** after editing; unsaved edits survive changes between the four destinations. Leaving the case prompts before discarding edits, and a failed save keeps the draft available for retry.
2. **Documents** accepts files through the chooser or drop area. Open a document to inspect its extracted text and preserved original. Folder/ZIP intake and document-use restrictions remain available here; uploading does not approve material for a simulation.
3. **Simulation** contains preparation, review and the explicit start action. Advanced preparation controls remain available. Loading a case or changing a destination never starts model generation.
4. **Results** shows the selected saved attempt. A completed attempt displays its recorded decisions, actual vote counts and named participants' reasons. Failed, stopped and incomplete attempts do not display a final decision. A split criminal panel is labelled **No unanimous decision** only when twelve distinct valid final ballots support that description.

Select a source reference to open its inspector alongside the result on a wide screen. On a phone, it opens in a focused full-screen dialog; closing it returns focus to the source button. A missing exact passage is explicitly marked. Source content is an assertion in the record, not proof that the assertion is true. Download the preserved original or copy its citation from the inspector.

**All cases** opens the case list and **Import saved case**. **Download case** exports the saved archive. The selected case, destination and attempt reopen without regeneration when browser storage is available; case content and decisions remain in the local database. Browser storage restrictions can prevent remembering the selected destination, but do not delete saved cases. No database migration is required for this interface.

**Advanced tools** opens the existing Decision and TrialForge workspaces. Provider settings and existing approval, privacy and source-check requirements continue to apply.

## Run Locally

```powershell
npm install
if (-not (Test-Path -LiteralPath .env.local)) {
    Copy-Item -LiteralPath .env.example -Destination .env.local
}
npm run dev
```

Open `http://127.0.0.1:5173`.

For a local OpenAI-compatible runtime, set:

```powershell
MODEL_PROVIDER=openai-compatible
OPENAI_COMPATIBLE_BASE_URL=http://localhost:11434/v1
OPENAI_COMPATIBLE_API_KEY=ollama
OPENAI_COMPATIBLE_MODEL=qwen2.5:14b
```

For external MiniMax calls, set `MODEL_PROVIDER=minimax` and provide `MINIMAX_API_KEY` in `.env.local`. The default model is `MiniMax-M3.1-Flash` and the default MiniMax base URL is `https://api.minimax.io/v1`. This is the GA model listed in the [official API guide](https://platform.minimax.io/docs/guides/text-generation). An explicit `MINIMAX_MODEL` value takes precedence, including existing preview-model configurations; setup does not rewrite an existing environment file.

Model calls use `MODEL_TIMEOUT_MS` and `MODEL_MAX_RETRIES` for timeout and retry/backoff control, `MODEL_MAX_OUTPUT_TOKENS` for the output budget (default 6,000 tokens on local runtimes and 16,000 on external providers, whose reasoning tokens share the budget), and `MODEL_TEMPERATURE` to override the per-stage sampling defaults.

When the API is bound to a non-loopback `HOST`, every route requires `LOCAL_API_TOKEN`, per-IP rate limiting is enabled (`API_RATE_LIMIT_PER_MINUTE`, default 240), and `TRUST_PROXY` should be set when a reverse proxy sits in front so the real client address is used. Loopback development is not rate-limited unless `API_RATE_LIMIT_PER_MINUTE` is set explicitly. Validation errors return 400 with the failing fields, missing records return 404, and runtime faults return a generic 500 whose details stay in the server log.

## Courtroom Realism

The **Courtroom protocol** option enables the new `courtroom_v1` path for an Ontario criminal jury Full Proceeding. It is opt-in while release review remains open. Use **Legal readiness** to prepare and attest a complete packet, save and approve the new case-model version, then start the proceeding. The run pins that packet; a material law change needs a new packet and run. Attestation records the reviewer and exact content hash and does not certify legal accuracy.

**Courtroom controls** manage witnesses, direct/cross/re-examination, objections, explicit judicial effects, jury absence/return and instructions. A paused examination or charge checkpoint requires the applicable command before resuming. **Participant memory** shows the selected actor's authorized record, instructions, assessments and open questions. Current exclusions and strikes affect future use while preserving the event history. Ballots must acknowledge the delivered instruction and explain a changed vote using a relevant visible event.

Document-use settings also accept permitted paragraph numbers, issue and party IDs, and prohibited purposes. Unknown or mismatched scope is withheld; original paragraph numbers survive projection. A reference cannot bypass these restrictions. Restriction meaning still needs semantic review. `npm run coverage:all` measures the isolated browser journeys alongside server tests and enforces 80% aggregate lines, statements, functions and branches. See the [release review worksheet](qa/courtroom-release-review.md) for independent behavioral and legal review.

Run `npm run test:courtroom` for the browser journey and `npm run eval:courtroom` for fictional scripted evaluations. Live evaluation is explicit (`npm run eval:courtroom -- --live`) and budgeted; see [evaluation details](evals/courtroom-realism.md). Coverage and dependency audit are current repository gates; check the candidate's CI results. The [release review worksheet](qa/courtroom-release-review.md) tracks independent behavioral and qualified legal review separately from mechanical checks and live source-verification acceptance.

The **Full Proceeding** workspace uses three separate procedure adapters: Ontario criminal jury, Ontario Capital Markets Tribunal, and Ontario civil (judge-alone or six-person jury). Procedure order and permitted moves are deterministic. Criminal guilt is decided only from twelve independent per-count ballots; OSC proceedings create no juror records; civil jury mode requires a valid jury notice and applies the five-of-six rule. Synthetic panels are not statistically representative and are not verdict predictions. The votes of a single run are not probabilities; the Strategy area's Forecast reports simulated-panel win probabilities from many runs, with intervals and sample sizes, and says they have not been tested against real outcomes.

Full-proceeding actors all use the server's configured model provider, which is stamped onto each run as `config.provider` for the audit trail; clients cannot choose a provider per actor. The external-disclosure confirmation is required for screen and full runs alike whenever that provider is external (MiniMax), and is not required on a local OpenAI-compatible runtime such as Ollama. Motion rulings, objection rulings, and per-issue findings ask the model for the exact permitted disposition vocabulary and record the answer directly. Witness answers are generated in role but bounded to the witness's approved statement segments: an answer that does not cite an approved segment is replaced by the approved statement, and recall gaps are recorded as "do not recall". `deliberation.maxRounds` is the number of deliberation turns per juror (one inventory turn, one review turn, and the rest spent on challenges). Actor context roles are derived from the roster rather than taken from the caller.

Disclosure analysis scores heuristic hits: a single reported-speech phrase is a low-severity finding, while explicit hearsay language, repeated reported speech, privilege language, and extraction defects are motion-grade. The motion docket consolidates every motion-grade concern on the same exhibit into one proposed motion with the union of permitted relief. Deleting a matter releases its original uploads and any content-addressed corpus blobs that no other matter still references.

Full-proceeding jurors are seeded from continuous cognitive traits (comprehension, numeracy, memory, ambiguity tolerance, confidence calibration, narrative susceptibility, burden sensitivity, assertiveness, patience, and social influence). They are not assigned Crown/defence outcome quotas and no outcome is inferred from demographic stereotypes. Initial and final ballots are isolated per issue; invalid calls remain explicit no-verdict/incomplete records and cannot be filled in by a group response.

A final ballot compares its position only with one usable initial assessment for that actor and issue. A failed or unavailable initial ballot cannot create a change of mind. In both legacy and courtroom proceedings, an actual change requires an explicitly selected usable deliberation event, an explanation, and a shared permitted source; the engine never assigns the last speaker as its cause. Earlier saved runs retain their original records.

Source checks distinguish dollar suffixes from following section labels and recognize numbered continuation pages with an interview/transcript header. This affects quotation comparison only: original text, spoken numbers, speaker changes, citation offsets and saved quotations remain intact. Peer agreement and own-history clauses are checked separately; a source quotation following agreement is still checked against that source. Checker retries identify the eligible named-peer records and require a fresh successful judgment. Author repairs must keep each proposition with its own source and mark quotation omissions explicitly.

Classify each source and identify whether the whole document or selected extracts were supplied. Record material outside the run as **Not supplied to this run** unless there is a separate basis for reporting a disclosure gap. Saving creates a new draft version; approve it before running. Existing proceedings keep their original model.

The paragraphs below describe the preserved **legacy fast simulation** workflow and its saved sessions.

Every simulation creates a fresh, session-stable jury pool from varied persona archetypes. Saved sessions keep their original jurors, but new runs sample a different balanced panel with distinct roles, skepticism levels, burden sensitivity, default leanings, and evidence focuses.

Panel size and the decision rule follow the real forum for each template:

- **Criminal Defence** - 12 jurors, unanimity required; anything less is treated as a hung jury.
- **Civil Dispute** - 6 jurors, agreement of at least 5 of 6 required (Ontario civil jury majority).
- **OSC / Securities** - a 3-member tribunal-style panel that decides by simple majority.

By default the jury deliberates in **independent secret-ballot mode**: each juror casts an independent ballot in its own model call (with retrieval personalized to that juror's evidence focus) before the panel deliberates together, so opinions are not generated in one correlated pass. The ballot is recorded as the first `secret_ballot` snapshot in each juror's belief trail, and a final vote that departs from the ballot without a deliberation-based explanation is flagged. Switch to the faster single-pass mode in Run Settings if you prefer one model call for the whole panel.

Before deliberation the judge delivers a charge to the jury (elements, burden and standard of proof, credibility and circumstantial-evidence guidance, and the decision rule), and the jury is instructed to apply it. Sampling temperature also varies by role: jurors deliberate at higher temperature for natural diversity, advocates argue at a middle setting, and the analyst, charge, and synthesis stages stay near-deterministic. Override with `MODEL_TEMPERATURE`.

The judge stage receives the structured jury deliberation record, including the split, the decision rule, the verdict status, and individual juror rationales, and is instructed to use realistic outcome language for the template (guilty/not guilty/hung jury; liable/not liable; allegations proven/not proven). Verdict confidence is calibrated from the model's ruling, jury consensus, the decision rule, juror confidence, citation warnings, and unresolved issues. High confidence near 90% is reserved for panels that actually met their decision rule with clean citations and limited proof gaps; a hung panel is capped and explicitly reported as unresolved.

## Upload Limit

The default upload limit is 250MB. Change it with `JUDGE_JURY_MAX_UPLOAD_BYTES` in `.env.local`; temporary upload files are written under `UPLOAD_TMP_DIR` and removed after extraction. ## Analysis jobs and cost limits

Analysis features run as jobs. Four job kinds are registered today: `chronology`, `chronology_readings`, `evidence_index` and `expert_assessment` (see the next section). Any other kind answers "no estimator registered". The job rules are:

- **Preview first.** `POST /api/matters/:matterId/analysis-jobs/preview` returns the estimated model calls and tokens (about 12,300 tokens per call, the project's measured average), the caps, and whether the job could start. It calls no model and stores nothing.
- **Start with the preview's hash.** `POST /api/matters/:matterId/analysis-jobs` must quote the `estimate.hash` from the preview. The estimate is recomputed when the job starts. If the matter or the parameters changed, the start is refused with 409 and the preview must be confirmed again.
- **Hard cap.** Each job has a cap on model calls and a derived cap on tokens. `ANALYSIS_MAX_CALLS_PER_JOB` sets the default. **The default of 500 calls is a placeholder: decision D6 (the spending limit) is still open with the owner.** A job whose estimate is over the default cap runs only when the request sets `acknowledgeCost: true` and a higher `maxCalls`. No cap can exceed the absolute ceiling of 5,000 calls (about 61 million tokens). A running job stops when it uses its budget: its status becomes `stopped_at_cap` and its partial results are kept. A job whose work was all finished when it used the last of its budget (for example, a cap equal to the estimate) ends as `succeeded`, not `stopped_at_cap`: a handler reports that it completed, and only work that was cut off counts as stopped. A capped job can be resumed only with a higher cap.
- **Queue.** At most `ANALYSIS_MAX_CONCURRENT_JOBS` jobs (default 2) run at once; others wait first-in, first-out.
- **Cancel and resume.** `POST .../analysis-jobs/:jobId/cancel` stops a queued or running job. `POST .../analysis-jobs/:jobId/resume` re-queues an interrupted, capped or failed job; its recorded usage keeps counting against the cap, and the job's handler decides from the stored parameters and partial results what is left to do. When the server restarts, jobs that were running or waiting become `interrupted`.
- **Statuses:** `queued`, `running`, `succeeded`, `failed`, `cancelled`, `interrupted`, `stopped_at_cap`.

Structured model calls used by these jobs go through the same provider settings as the rest of the app, including its retry and time limits. An external provider is refused unless the external-disclosure confirmation is given. Imported documents are placed in the prompt as untrusted data inside delimiters, never in the instructions. A document longer than the 240,000-character actor limit is listed as failed with its reason; it is never truncated or skipped silently.

## Case timeline, evidence index and expert assessment

These three features prepare a case: they sort what the record says into a timeline, a catalogue and an assessment of each expert. The server side and the screens are built and tested with a scripted model; the screens are described under **The Facts & Evidence screens** below. **Extraction quality has not been measured on a live model.** The plan's target of 90% precision and recall for extraction is unverified: the tests prove the software around the model (source checks, date checks, merging, review, access limits), not how well any real model reads a record. Every model call is estimated (one call per document for each extraction, two per expert report for experts, one per key fact for readings), previewed and capped as in Analysis jobs above. Each result is a versioned draft artifact that a person reviews and approves; nothing is regenerated automatically. Results are preparation material: they never reach a simulated juror or witness.

**Timeline and key facts**

- **Dates are read by code first.** A program finds dates in each document's text (ISO dates, "March 3, 2023", "3 March 2023", month-only, year-only, ranges, "approximately", email `Date:` lines) with the paragraph each came from. A file's modified or upload time is never an event date. A numeric date such as 04/05/2023 that could be day-first or month-first stays unknown, with both readings and the original text kept; it is never guessed.
- **A model proposes events, one call per document.** Each event has a date (precision, start, end and the original text), a description, a type, an assertion (`record`, `testimony`, `allegation` or `inference`), the quoted passages that support it, and issue links. The server checks every quoted passage against the preserved text. An event whose passage fails is refused and listed with the reason, never dropped silently. The date is checked too: its original text must appear in the cited passage and the date (and time) it resolves to must be one the program finds in that paragraph. If not, the date becomes `unknown` and the event says why. A claim typed `record` that comes from a pleading or an examination transcript is retyped `allegation` or `testimony`, because a document showing that someone said something does not show it is true.
- **Merging and conflicts are done in code.** Events with the same date, the same assertion type and similar wording merge, and keep every source. Events on one day with different times and similar wording, or on different days when the model labelled both as the same one-time occurrence (`eventKey`), are flagged as a possible conflict. Repeated events such as clinic visits are not flagged. Events with an unknown date are never merged or compared.
- **Review queue.** Accept, reject, reset or edit each event. Every decision saves a new draft version; older versions are never changed. Approve the draft to expose its accepted events. Only accepted events of the approved timeline are available to later features.
- **Key facts** are the accepted events ranked by issue links, dispute (a flagged conflict) and number of source documents. Promoting a key fact to a disputed fact saves a new case model version; the approved model is not edited.
- **Juror-style readings** (three to five per key fact, in three lenses: plain-language, likely question, which way it cuts) use only passages jurors may see under the matter's admission settings. Excluded, reserved, hidden and redacted material never reaches the model, and the event description is not sent either (it may come from material jurors cannot see). With no admission settings saved, nothing is admitted and no reading is produced. Until a jury profile exists, readings are labelled `not venue-based`. They are labelled as simulated model output. If the admission settings change afterwards, the readings are withheld until written again.
- The timeline and index are tied to the evidence they were prepared from (hashes), not to a case model version, because promoting a fact or accepting a suggestion makes a new model version by design.

**Evidence and testimony index**

- The index is a read model. It is computed whenever it is read from the exhibits and their passages, the case model's evidence matrix, disputed facts, witness statements, theory claims, disclosure findings and the model's catalogue entries (testimony units with speaker and examination type, allegations, admissions and expert opinions). Admission status comes from the matter's admission settings at that moment: change a ruling and the next read shows it, with no regeneration.
- **Allegations are never counted as evidence.** Each entry has an assertion type, and `countsAsEvidence` is worked out from the type on every read: allegations and inferences never count, and neither do theory claims, disputed facts or findings. Coverage ignores matrix links to allegations (it shows them as `allegationOnly`).
- **Suggested mappings are proposals.** A suggestion (passage to element to verdict question) changes nothing until accepted. Accepting saves the passage into the evidence matrix as a new case model version, through the same path as the matrix editor, which you then approve. A suggestion that is rejected or ignored changes nothing.
- **Coverage** lists elements with no supporting evidence, elements with no contrary evidence, sources mapped to nothing, and record gaps. Code finds the gaps a source states in its own words ("have not been received", "not enclosed", "undertaking outstanding", "overwritten"). It cannot find an absence no source mentions (for example, a missing weather record); the model can propose one, and the record scope's missing materials are included.

**Expert assessment**

- One call extracts each expert's record from the report (field, who retained the expert, qualifications, compensation, data relied on, assumptions, and each opinion with its source; opinions are typed `expert opinion`) and one call assesses it. `qualificationsStated` is computed from the qualifications that passed the source check: a court file number such as `CV-23-00012345-0000` or an attached CV is not a stated qualification. The disclosure analysis's expert-foundation flag no longer reads the letters "CV" in a court file number as a qualification.
- Code reads the indicators it can from the text and cites the line: no stated qualifications, no stated compensation, a share of retainers from one side of 75% or more, an examination under 30 minutes, "did not review" statements, and assumptions stated without a basis. Those thresholds are stated choices, not findings of bias.
- **Optional model check.** Off by default. Tick **Also check each claim with a model (costs more calls)** in the generate controls and every opinion and finding that passed the code check is also put to a second model call (up to five per call) that says whether the passages it cites support it, as described under Case summaries: unsupported items are refused and listed, undecided ones are badged **Not confirmed by model check**, and unchecked ones **Not checked**. An assessment left with no supported finding is rejected as a whole. The cost preview assumes up to 12 statements for each report. There is no expert export, so the verdicts show on the screen and in the saved draft.
- **Every finding must cite the record.** A finding with no cited passage, or whose passage is not in the record, is refused. A claim about an expert's reputation needs a cited passage that says so. An assessment with no valid finding is rejected as a whole. Opposing experts' opinions are grouped by topic side by side; code does not decide whether they conflict.
- **Readability and jargon density** are computed in code (Flesch reading ease and Flesch-Kincaid grade, plus the share of words on a short list of medical, economic and legal terms). This is a stated heuristic for how hard a text is for a lay reader. It is not a measure of what a juror understood.
- **Admissibility criteria** come from a reviewed rule pack and are unknown by default: the assessment then says so and offers no admissibility conclusion. The API does not accept criteria from a request body. Juror impact is a typed hook only (`jurorImpact` is `null`); when it exists it will be labelled simulated.

**The Facts & Evidence screens**

The **Facts & Evidence** destination in the case navigation holds three tabs: **Timeline and key facts**, **Evidence and testimony index** and **Expert witnesses**. The tabs move with the arrow keys, Home and End, and the tab you last used is remembered for the case. Each screen says that its output is a model-generated draft until a person approves it, shows a cost preview (estimated calls and tokens, and the cap) before any model call, asks for the external-disclosure confirmation when the provider is external, follows the running job, and shows a banner when the result is out of date. Nothing is regenerated for you.

- **Timeline and key facts.** Events appear in a table by date, each with how precise the date is and the date text as written in the source. A source that states no date leaves the event as **Date unknown**; nothing is filled in. Allegations and inferences are labelled as not proof and not evidence. Filter by type, what the source does, review state (rejected events stay visible), issue and conflict. **Treatment by provider** groups treatment events by provider and facility. Conflicting events are shown side by side with their sources. Accept, reject, reset or edit each event (the edit form is inline and labelled, marks the event as edited, and shows the server's reason if a date is refused), then **Approve chronology**; after approval an edit saves a new draft. Key facts show rank and the reasons for it. **Promote to disputed fact** creates a new draft case model version (the approved model is not edited). **Write juror-style readings** has its own cost preview and is labelled **Simulated model output**, with its basis (`not venue-based` until a jury profile applies); readings are hidden if the admission settings changed since they were written. Items the source check refused and documents that could not be read are listed.
- **Evidence and testimony index.** A paged, filterable table (entry type, source type, exhibit, issue, element, admission status, counts as evidence, text search). Every row opens its source passage. An entry that is not evidence (an allegation, an inference, a theory claim, a disputed fact, a finding) says **Not evidence**. Admission status is shown for each source and read live from the saved admission settings. The coverage view shows elements with no supporting or no contrary evidence, sources mapped to nothing, and record gaps with where each came from. Model suggestions are listed as proposals that change nothing until you **Accept proposal**, which saves the passage into the evidence matrix as a new draft case model version; **Reject proposal** changes nothing in the case model. Then approve the index.
- **Expert witnesses.** One card per expert: the record (field, retained by, qualifications, compensation, data relied on, assumptions, each with its source and a plain "not stated in the report" where the report says nothing), opinions typed as expert opinion, indicators read from the text (concern or information, with the passage), findings grouped by dimension with their cited basis, and readability with the stated-heuristic note. Opposing experts are compared opinion by opinion in a table. Admissibility reads **unknown — court rules not entered** until reviewed court rules supply criteria. Juror impact is shown as unavailable and labelled simulated. Then approve the analysis.

**API** (all under `/api/matters/:matterId`; bodies and queries are validated and unknown keys are refused)

- Chronology: `POST /chronology/generate/preview`, `POST /chronology/generate` (needs `estimateHash`), `GET /chronology`, `POST /chronology/events/:eventId/review`, `POST /chronology/approve`, `GET /chronology/accepted`, `GET /chronology/key-facts`, `POST /chronology/key-facts/:eventId/promote`, `POST /chronology/readings/preview`, `POST /chronology/readings`, `GET /chronology/readings`.
- Evidence index: `POST /evidence-index/generate/preview`, `POST /evidence-index/generate`, `GET /evidence-index` (filters `type`, `assertion`, `exhibitId`, `issueId`, `elementId`, `admission`, `countsAsEvidence`, `q`, `page`, `pageSize`), `GET /evidence-index/coverage`, `GET /evidence-index/suggestions`, `POST /evidence-index/suggestions/:id/accept`, `POST /evidence-index/suggestions/:id/reject`, `POST /evidence-index/approve`.
- Experts: `POST /expert-assessment/generate/preview`, `POST /expert-assessment/generate`, `GET /expert-assessment`, `POST /expert-assessment/approve`.

## Case model verdict-form fields

A case model can carry optional fields for the verdict form. Models saved without them keep working. A decision issue can have `questionText`, `decider` (`jury` or `judge`), `answerType` (`choice`, `amount` or `apportionment`), `dependsOn` (ids of other issues in the same model, with no cycles) and `order`. A witness can have a `kind` (`fact`, `party` or `expert`). A document in the record scope can have a `documentType` (`pleading`, `medical`, `expert_report`, `transcript`, `correspondence`, `financial` or `other`), which is separate from its existing `kind`. These fields are stored and archived. Marking an issue `judge` keeps it from jurors: see Court rules below. The other fields do not change how a simulation runs yet.

## Court rules

Court rules say how a civil jury trial works where the case is heard: whether there is a jury, how many jurors, how many must agree, what happens if a juror is discharged, and the rules that later features will need (fault, damages caps, punitive damages, interest, the order of damages calculations, whether counsel may suggest amounts, and when an expert's evidence is admissible). They come from a **rule pack**: a dated, versioned set of rules, each with the authority and pinpoint it comes from. The first pack is `ontario_civil_2026_11` (Ontario civil jury trials, Courts of Justice Act s. 108 and s. 118, Negligence Act s. 3, and the Supreme Court cases on expert evidence and punitive damages).

- **These rules have not been reviewed by a lawyer.** Every pack ships unreviewed, and every screen and response says so (`unreviewed: true`). A pack shows as reviewed only while a named reviewer's attestation matches the exact version; any edit, including a change for one case, removes it. Statute wording was read from an unofficial source and still needs checking against e-Laws. No case proposition has been verified; those rules carry "reviewer to confirm" and "to be confirmed".
- **Unknown is not none.** A rule nobody has entered is `unknown`. It is never read as zero or as "no limit". The seed pack leaves the non-pecuniary damages limit and how it is indexed, the punitive damages standard, interest, collateral benefits and the order of damages calculations unknown. Anything that depends on an unknown rule is blocked, with an error that names it. A civil jury run needs the jury availability, the panel size and the decision rule; judge-alone does not.
- **Dated.** Each rule has an as-of date. Rules last confirmed more than 180 days ago show a stale warning.
- **Choosing rules for a case.** The Court rules panel on the case Overview shows the pack, the panel size and decision rule a new civil run will use, every rule with its status, authority, date and review state, and any changes made for this case. Choose a pack and enter your name to save. `GET /api/frameworks`, `GET /api/frameworks/:packId`, `GET /api/matters/:matterId/framework` and `PUT /api/matters/:matterId/framework` (`{ packId, changedBy, overrides: [{ field, status, value, reason, authorities }] }`) do the same. A change for one case replaces one rule, records who made it and when, and makes the pack's hash differ from the curated one, so it is unreviewed until someone reviews that exact version.
- **Pinned to each run.** A civil run created after rules are chosen takes its panel size and decision rule from them (the default is still six jurors with five deciding when no rules are chosen), cites them in the instruction jurors receive, and stores them with the pack hash on the run. Later changes to the rules never change an earlier run. If five jurors remain after a discharge, the decision function applies the reduced-panel rule (Courts of Justice Act s. 108(8): unanimity); the rule is used only when court rules are pinned, and the engine reads discharges from `juror_discharged` events, which nothing in the application records yet.
- **Questions for the judge.** An issue with `decider: judge` (or a kind the pinned rules reserve for the judge) is never put to jurors: the engine records no juror ballot for it, a juror ballot sent for it is refused, and its decision is the judge's finding. Jurors are also not given its instructions. Only civil cases support this.
- **Answers on questions the defence must prove.** A juror's leaning is by side. On a question the defence must prove (for example contributory negligence), the juror is told what the leaning means and a leaning for the defence side now records the answer that the question is established. Before this change the answer was recorded the other way round.

## Case map (legal issues)

The **Case Map** destination reads your pleadings and shows the claims, defences, crossclaims and relief they contain, who pleads against whom, and the questions a jury could be asked. It is for preparation. Pleadings state what a party alleges; the map never treats an allegation as proved.

- **Generate.** **Generate case map** first shows a cost preview: one model call for each pleading plus one to suggest elements, the estimated tokens, and the cap. Nothing is read until you choose **Start reading the pleadings**. With an external provider you must also confirm the disclosure. Only pleadings are read: documents classified as a pleading in the record scope, or recognised as one from their title (a statement of claim or defence, a crossclaim, a jury notice). A document the model fails on, or one over the size limit, is listed as unreadable, never dropped silently. Pleadings are sent to the model as untrusted data inside delimiters; text in a pleading that looks like an instruction is not followed.
- **Checked quotations.** Every item cites a quotation. The server finds it in the preserved pleading, records the pleading's own paragraph number, and rejects the item if the words are not there, if they are not inside a numbered paragraph of a numbered pleading, or if the item names a party it cannot tell apart. Rejected items stay visible with the reason. A line placed directly under a numbered paragraph reads as part of that paragraph, so this check narrows what a pleading can smuggle in; it does not make pleading text trustworthy. Read each item against its source.
- **Parties.** Parties come from the case model. A pleading may name a party the model lacks (shown as proposed); applying the map adds it.
- **The matrix.** One row for each claim or crossclaim, one column for each party it is pleaded against, with words in every cell. **Show details** opens a row to its elements, who bears the burden (the party that pleads it), the evidence already mapped to each element, and the pleading passages, each with a link to the preserved source. Defences, factual questions and damages follow in a second table. Denials, pleaded facts, interest and costs are not jury questions and are listed separately.
- **One question per claim per defendant.** A claim pleaded against two defendants becomes two questions, so results for each defendant need no new ballot type. An affirmative defence becomes a defence question that the pleading party must establish. A defence that puts one fact in issue becomes a yes or no question. Each head of general, special or punitive damages becomes a damages question; simulated jurors answer whether the head is established, not an amount.
- **Verdict form in answer order.** Liability, crossclaims, defences, then damages, each with the questions it depends on.
- **Elements.** Elements come from a reviewed legal packet (one attested against its exact content) or the question already in the case model, so edits you made survive. The rule pack holds no claim elements yet. Otherwise a model suggests elements; they are marked as suggested by a model and not checked against law. A question with no elements gets a placeholder, and a placeholder blocks approval until you state the elements or leave the question out. You can edit elements per question.
- **Judge-only questions.** A question of a kind the matter's chosen court rules reserve for the judge is marked so, and jurors never receive a ballot on it. You can also mark a question yourself. If the rules do not say, or none are chosen, nothing is marked from the rules and the screen says so. The screen carries the **not reviewed by a lawyer** notice whenever the rules are unreviewed.
- **Approve, then apply.** Generating or approving changes nothing in the case model. **Apply to case model** (after approval) saves a new draft version of the case model; the approved version is never edited. Questions already in the model that the map does not name are kept unless you choose to replace them; evidence links to replaced questions are dropped and counted. Applying twice is refused. A map applied to the model records that fact and stays current.
- **Out of date.** The map records the case model version, the evidence hashes and the chosen rule pack. If a document is added or removed, the case model changes, or the court rules change, the map shows **out of date**; it can no longer be reviewed, approved or applied, and it is never regenerated for you.
- **Quality is not verified.** Tests use a scripted model that returns the answer key. How well a live model extracts claims, defences and parties from real pleadings has not been measured.

API: `POST /api/matters/:matterId/case-map/generate/preview` and `/generate` (`{ estimateHash, maxCalls?, acknowledgeCost?, providerMode?, externalDisclosureConfirmed?, evidenceIds? }`), `GET /api/matters/:matterId/case-map`, `POST /api/matters/:matterId/case-map/issues/:issueKey/review` (`{ included?, decider?: 'judge' | null, elements?, note? }`), `POST /api/matters/:matterId/case-map/approve` and `POST /api/matters/:matterId/case-map/apply` (`{ replaceExisting? }`).

Reviewed legal packets now also accept `proceeding: ontario_civil_v1`, with the same attestation, hash and placeholder checks as criminal packets. The courtroom protocol (`courtroom_v1`) is still for criminal jury proceedings only.

## Case summaries (both sides)

Open **Case Map**, then **Case summaries**. A summary is private preparation for one side: its theory of the case, the facts with citations, the claims and elements with the burden, the instructions and precedent to expect, witness credibility, its own acknowledged weaknesses, and a walk through the verdict form in answer order. It is a model-generated draft, it is not a prediction, and simulated panels and ballots are not real verdict probabilities. These labels appear on the screen and in every export.

- **Choose a side.** The plaintiff is chosen first; any party of the case model can be chosen. Each side is written in its own model call from the neutral record (accepted timeline events, evidence that counts as evidence, the approved case map, approved expert findings) plus that side's own private theory. The other side's theory, notes and summary are never sent. A summary never reaches a simulated juror or witness.
- **What it is built from.** The screen lists each input as available, missing or not applicable. An approved case map, an approved timeline and an approved evidence index are required: if one is missing, the summary says so in plain words and cannot start. An approved expert assessment, chosen court rules and the side's own theory are optional; when they are missing the summary says what was written without them.
- **Cost.** **Generate summary** shows a cost preview first: one model call for each side chosen, the estimated tokens and the cap. Nothing is sent until you choose **Start writing the summary**. With an external provider you must also confirm the disclosure.
- **Checked citations.** Every sentence cites a passage. Code confirms the quotation is in the preserved source; a sentence with no citation, or one that fails the check, is rejected and listed with its reason under the rejected sentences. A passing check shows the passage exists, not that the sentence reads it correctly.
- **Law comes from approved sources only.** Expected instructions come from the curated instruction sections for the procedure and the chosen court rules' authorities. Precedent comes from the court rules' authorities. A sentence that names a case, statute, rule or citation outside that list is refused. Points the sources do not cover are marked **Needs research**. Court rules that no lawyer has reviewed are labelled as such, and so is every authority taken from them.
- **Optional model check (tier 2).** Off by default. Tick **Also check each claim with a model (costs more calls)** before **Generate summary**, and each sentence that passed the code check is also put to a second model call, in batches of up to five, which says whether the passages it cites support it. Only the sentence and those passages are sent (never either side's theory, the case map or any other document), and the call goes through the same provider, disclosure confirmation, retry and time limits as the rest of the run. A sentence the checker finds unsupported is rejected, with its reason, under the rejected sentences. One it cannot decide is kept and badged **Not confirmed by model check**. One that was not checked (the checker failed, or the run reached its cap or was cancelled) is kept and badged **Not checked**; it is never counted as confirmed, and a run cut short by its cap ends as `stopped_at_cap`. The draft records the check (the prompt version, how many sentences were confirmed, not confirmed, rejected and not checked, and each verdict) and its input manifest says a check was on, so a checked summary is never mistaken for an unchecked one; exports show the same. The cost preview adds the checker calls to the estimate. The number of sentences is not known until the summary is written, so the estimate assumes up to 40 sentences for each side (8 checker calls); it is an upper bound on what is expected, and the calls actually made follow the real number. A passing model check is a second opinion from a model, not proof: a lawyer still reads the passages. The check was proven with a scripted checker only; how well a live model judges support has not been verified. Through the API, send `"modelCheck": true` in the body of the preview and of the generate request of case summaries, expert analysis and the improvement plan (the preview then also returns a `modelCheck` object with the checker calls, the batch size and the assumed number of statements); the setting is part of the estimate hash, so a request for the other setting is refused with 409 until previewed again.
- **Approve, then use.** Approving marks a version as reviewed by you. Generating or approving changes nothing in any simulation. **Use as theory** (approved summaries only) first shows the current private theory it will replace, then, after you confirm, saves a new draft case model version whose private theory for that side is the theory of the case. The earlier version is not edited. Approve the new version in Overview before a simulation uses it. **When the summary was made with the optional model check, only the theory sentences the check confirmed are carried.** A sentence the check could not decide (badged **Not confirmed by model check**) or did not check (badged **Not checked**) is left out, and the preview says how many were left out and why, and lists them, before you confirm. If the check confirmed none, there is nothing to carry and the confirm button is off. To carry them anyway, tick **Also include sentences the model check did not confirm** (off by default); the preview is shown again with them, and each one stays tagged in the theory text, **[not confirmed by model check]** or **[not checked by model check]**, and is recorded by its sentence id in the summary's use-as-theory record, so the new case model version shows they were not confirmed. Once the theory is saved, the summary says what the check did, next to the note that it was saved as the private theory: **Model check when this was used as theory: N sentences carried, N not confirmed, N not checked, N left out**, followed by whether the sentences not confirmed were left out or were included because you chose to. It gives counts only, quotes no sentence, is read from the saved summary so it is still there after a reload, and is not shown when the summary was made without the check. In **Private theories** (Simulation, under Advanced preparation), a theory whose text carries one of the two tags shows a short note that those sentences were not confirmed by the model check. That note is read from the tags in the text, because a saved theory does not itself record that a check ran; it goes away if you edit the tags out. A summary made without the model check is used exactly as before: nothing is left out or tagged, and the option has no effect. Through the API, the preview is `GET /api/matters/:matterId/case-summary/:partyId/use-as-theory` (add `?includeUnconfirmed=true` to include the others) and the confirmation is `POST` to the same path with `{"confirm": true, "includeUnconfirmed": true}`; `includeUnconfirmed` must be a boolean (anything else is refused with 400), and the preview and the result then carry a `modelCheck` object with the counts (`carried`, `notConfirmed`, `notChecked`, `leftOut`), the left-out sentences and `canUse`. The rule was proven with a scripted checker only.
- **Export.** **Download Markdown** and **Download HTML** carry the labels, what was and was not available, citations resolved to exhibit and paragraph, the authorities with their review state, the needs-research points, the rejected sentences and an unreviewed-court-rules notice when the rules are unreviewed.
- **Out of date.** A summary is marked out of date when a document is added or changed, the court rules change, or a newer case map, timeline, evidence index or expert assessment is approved. Nothing regenerates for you.

Live-model summary quality has not been verified: the tests use a scripted model.

## Local jury profile

The **Local jury profile** panel on the case Overview turns datasets you import into a venue profile: a likely jury pool, attitude distributions, a summary of verdict observations, and the strata used to sample synthetic jurors. **No real venue data ships with the app and nothing here is calibrated.** The repository holds only clearly fictional files in `samples/venue-fictional/`. Nothing is fetched from the web and no model is ever asked for a statistic.

- **Datasets.** Import JSON with `name`, `kind` (`population_table`, `attitude_survey`, `focus_group` or `verdict_observations`), `source`, `retrievedAt`, `licence` and `rows`. A dataset or row without a source or licence is refused, as is an unknown field, and the whole import fails with each problem listed. Attitude rows use a closed list of attitudes (scepticism about damages claims, trust in experts, scepticism about corporate defendants, experience with litigation, comfort with numbers). Focus-group text that names a protected personal characteristic is refused.
- **Population is not the jury pool.** Who may serve comes from the matter's court rules (`juryEligibility`; each criterion names a yes/no column of the population table). If the rules do not say, and the Ontario seed pack leaves it unknown, nothing is adjusted and the result is flagged. You can record the criteria for one case as a court-rules override. The response rate (low, central, high) is your stated assumption, and groups the table cannot classify are never counted as eligible.
- **Verdict observations.** Each has a court, year, claim type, outcome, award and source type. Raw figures are shown beside figures re-weighted by 1 / your assumed chance that such an observation was reported (by source type, outcome and award band), with a range across the low, central and high assumptions and seeded bootstrap intervals. Below 30 decided observations the screen shows an **Insufficient data** card with the count and no adjusted figure; award figures need 30 awards, and an attitude needs 30 respondents. Every screen carries the warning that tried cases are a selected group, so these patterns are not a win rate for any case (Priest and Klein, 1984), and that media-derived data skews toward plaintiff wins and large awards (Bailis and MacCoun, 1996).
- **Culture notes** (API only) are accepted only with a citation: a web address or a reference to one of the case's documents by hash. Uncited notes stay visible as rejected.
- **No demographic advice.** Synthetic jurors are described only by attitude and experience strata. The profile uses no protected personal characteristic and gives no advice about keeping or removing any person.
- **Build, approve, pin.** A build is deterministic and saves a draft; approving it first rebuilds it from the datasets and refuses it if a figure does not reproduce. It shows out of date when a dataset is removed or the court rules change. To use it in a run send `juryProfileHash` (the approved profile's hash) in the run configuration: the server pins the strata and replaces four juror traits (numeracy, comprehension, narrative susceptibility, burden sensitivity) from seeded draws of the strata, as a stated heuristic. Every other trait, and every run with no profile, is drawn exactly as before.

API: `GET|POST /api/matters/:matterId/venue/datasets`, `GET|DELETE /api/matters/:matterId/venue/datasets/:datasetId`, `GET /api/matters/:matterId/jury-profile`, `POST .../jury-profile/build` (`{ datasetIds?, assumptions: { responseRate?, reporting[], awardBandEdgesCents[] }, seed?, cultureNotes? }`), `GET .../jury-profile/:artifactId`, `POST .../jury-profile/:artifactId/approve`, `POST .../jury-profile/sample` (`{ artifactId?, seed, count }`).

## Deeper simulation: ballot contract v2 and juror cognition

In **Simulation**, **Run simulation**, the group **Deeper simulation (optional)** has opt-in settings. They are off unless you switch them on, a run keeps the settings it was created with, and a run that leaves them off sends exactly the prompts and reaches exactly the decisions it always did (a regression test compares two full scripted runs with a recording made before these settings existed). They all need jurors: they are unavailable for a judge-alone civil run, for the Capital Markets Tribunal and for the reviewed courtroom protocol (`courtroom_v1`).

- **Ballot contract v2** (`ballotContract: 'v2'`). A juror names one permitted outcome directly instead of returning a crown or defence leaning that code translates. The ballot also records `elementFindings` (one per element of the question: met, not met or undecided, with a confidence from 0 to 1 and cited sources), and, where the question asks for them, `amounts` (a category, whole cents, a three-letter currency and a basis) and `apportionment` (a share per party that sums to 100). The checks are: the outcome is permitted (an initial ballot may also say undecided), every element is covered once and belongs to the question, a "met" finding cites a source, amounts are non-negative whole numbers, shares are between 0 and 100 and sum to 100, and the outcome does not contradict the findings (every element met but the question denied, or any element not met or undecided but the question established). **A ballot that fails a check is saved as invalid with the reason and is never corrected.** The decision counts it as a missing ballot, so the question shows as incomplete. The basis text of each finding and amount goes through the same source check as the rest of the ballot. Straw polls are trial events, not a third ballot round.
- **Juror cognition** (`jurorCognition: true`). After every opening, direct examination, cross-examination and closing, each juror makes a private appraisal through one model call: comprehension, emotional direction (valence) and intensity, speaker credibility, what the juror noted, what they still wonder, and element-level shifts with sources. The model sees only that juror's admitted record; excluded, reserved, hidden and redacted material is filtered before the call as for every other juror call. The appraisal is checked in code (a value out of range is refused, and a shift naming an element that is not the jury's, or citing nothing the juror may use, is set aside with its reason; nothing is repaired) and is saved as an event visible only to that juror and the system. No other juror, witness, counsel or judge receives it, and an analysis artifact never reaches a juror. A failed call is saved as a failure, not invented.
- **Attention and fatigue are a stated heuristic, not a measurement.** They are computed in code from the length of the record the juror has heard, the position in a six-hour court day (assuming 40,000 characters of record per hour), the segment's complexity, figures in the segment, and the juror's traits, with a small jitter seeded from the run seed so the same run always gives the same values. The constants are assumptions, not calibrated.
- **All ten traits** reach the juror's prompts when cognition is on (ballots, deliberation and appraisals). When it is off, only the four that were always used are read.
- **Jury roles** (facilitator, driver, mediator, quiet juror, or participant) are derived in code once, before the charge, from the traits and the appraisals recorded so far, and saved for the system view. Each carries an airtime and speaking-order weight, which only the deliberation forecast (below) applies; a run without it does not. The foreperson presides and never controls the vote.
- **Cost.** The preview adds jurors x moments model calls when cognition is on (for example 6 jurors x 4 moments = 24, or 6 x 6 with one witness), once and not doubled, because appraisals have no second source-check call. A scripted run matches the preview exactly; for a live provider the screen states a margin of 25% for retries, which has not been measured. Witness examination calls themselves are still not counted, as before.
- **Results.** A completed run's **Juror journey** (Results) shows, for each juror, a table of simulated appraisals by moment with emotional highs and lows, attention and fatigue tables with bars, the derived role and the ten traits, and the panel's highest and lowest moments. Every row links to its saved transcript event. The screen and every appraisal event say **Simulated — model output and heuristics, not measurements.** Nothing is shown while the run is still going; like the rest of the owner audit it appears once the run has completed.

**Live-model behaviour of the appraisals and of v2 ballots is not verified.** Every test uses a scripted model: it proves the software (privacy, validation, storage, archives, the cost arithmetic, the screens), not whether a live model returns usable appraisals, follows the v2 contract, or produces plausible emotional or attention values. Simulated forgetting is out of scope.

API: `POST /api/matters/:matterId/trials` accepts `ballotContract: "v2"` and `jurorCognition: true|false` in `config` (any other contract value, or either setting for a judge-alone, tribunal or `courtroom_v1` run, returns 400). The server pins them in the run's `config`; `false` leaves no trace. `record_ballot` accepts `elementFindings`, `amounts` and `apportionment`. `GET /api/trials/:runId/cognition` returns `{ runId, simulated: true, label, heuristicVersion, heuristicNote, enabled, available, reason?, ballotContract: "v1"|"v2", view? }`; `available` is true only for a completed run with cognition on, and `view` has `segments` (key, kind, label, speakerId, phase, momentEventId, momentSequence), `jurors` (jurorId, isForeperson, the ten `traits`, derived `role`, `appraisals`, `failures`, `attentionSeries`, `highest`, `lowest`), `panel` (`perSegment`, `highs`, `lows`), `roles` and `forepersonControlsVote: false`.

## Deliberation forecast: straw polls, camps and friction

In the same **Deeper simulation (optional)** group, **Deliberation forecast** (`deliberationForecast: true`) is off unless you switch it on, a run keeps the setting it was created with, and a run that leaves it off makes exactly the calls and saves exactly the events it always did (a golden regression test records the full set of prompts, events, ballots and decisions of two runs from before the feature existed and holds every run that does not opt in to it). It needs a jury: it is refused (HTTP 400, nothing saved) for a judge-alone civil run, a tribunal and a `courtroom_v1` run, like the other two settings.

- **A straw poll after each round of challenges.** `maxRounds` is one inventory round, one review round and the rest challenge rounds (three is one challenge round, five is three). After each challenge round every juror privately states where they now stand on every question the jury decides, through the same ballot call (v1 or v2). A change from their last stated position must name the visible deliberation event that moved them, exactly as a changed final ballot must; one that does not is saved as an invalid vote and is not counted, never repaired. A straw-poll vote is a trial event visible to that juror and the system, not a ballot: the stored ballots, and the two-value `round` of `issue_ballots`, are unchanged.
- **Whether the jurors see the counts.** `strawPollCounts` is `visible` (the default, a show of hands as in a real room) or `hidden`; the server pins it into the run, and the screen offers it as **Jurors are told the straw-poll counts**. When visible, the jurors' later turns and ballots carry the counts (how many on each answer, never who). When hidden, no juror request contains them; the counts are still saved for the audit view. Each juror's own vote stays private either way, and the straw-poll counts event is saved visible to the jurors only when the run says so.
- **A reply target and a stance on every turn.** Each deliberation turn also records `stance` (agree, challenge, question or new_point) and `replyToEventId` (the earlier contribution it answers, with the juror it came from). The model returns them; the engine accepts a reply target only if it is an earlier contribution by another juror that this juror could see, and records the reason on the turn (`structureProblems`) for anything it cannot accept. They are never repaired or invented.
- **Order and airtime.** Speaking order is a seeded weighted draw from each juror's derived role and assertiveness (`speakingOrderWeight`), the same for the same run seed. A challenge round still has one turn per juror in all, so the number of turns, and the cost, does not depend on the roles; the airtime weight decides who takes them, by the highest-averages method (a driver may take two turns and a quiet juror none). The inventory and review rounds give every juror one turn in a seeded order. Roles are derived from the traits alone when juror cognition is off. The foreperson presides and never controls a vote.
- **Camps, friction, holdouts, who moved whom and the vote path** are computed in code from what the run saved, by fixed rules that the screen states (a model is never asked). A camp is jurors who finished on the same answer to every question, with the same element findings where recorded. A challenge is unresolved when the juror it answers has not changed a vote by the next vote; it scores 1, and 1 more when that juror challenged back in the same window. A holdout never changed their answer while at least two thirds of the valid final votes went another way. A move is a change between two valid votes, caused by the contribution the juror named, when that was a juror's. A panel that does not reach the decision rule is reported as **no agreement**, with the final ballots as cast; nothing forces a consensus.
- **Cost.** The preview adds jurors x questions x challenge rounds model calls (for example 6 x 1 x 1 = 6), counted twice in the expected total because each vote is a source-checked ballot. It adds no deliberation turns. A scripted run matches the preview exactly (the tests count the requests); a live provider may use up to the stated 25% more.
- **Results.** A completed run's **Deliberation forecast** (Results, below the Juror journey when both are on) shows the vote by round (a table, with a bar repeating each row's counts), each juror's votes by stage, the camps, the challenges with their friction scores, the holdouts, who moved whom, and the derived roles, weights and speaking order, each linked to its saved transcript event. **Across all completed runs of this matter** shows how often each final split occurred and how initial splits turned into final outcomes, for runs made with or without the forecast. Every screen and event says **Simulated**. Nothing is shown while the run is still going.

**Live-model behaviour of deliberation is not verified.** Every test uses a scripted model: it proves the software (privacy, storage, archives, the arithmetic, the screens), not whether a live model names a real earlier contribution as its reply target, chooses sensible stances, explains a change of position with a visible event, or is source-checkable when it mentions the straw-poll counts. The role weights, the airtime rule and the friction score are stated assumptions, uncalibrated, and a synthetic panel is not a real jury.

API: `POST /api/matters/:matterId/trials` accepts `deliberationForecast: true|false` and `strawPollCounts: "visible"|"hidden"` in `config` (the second only with the first). `GET /api/trials/:runId/deliberation` returns `{ runId, simulated: true, label, algorithmVersion, enabled, available, reason?, strawPollCounts: "visible"|"hidden"|null, view? }`; `available` is true only for a completed run with the forecast on, and `view` has `jurors` (jurorId, role, weights, turns), `speakingOrder`, `votePaths` (per question: `stages` with counts, invalid, missing and the poll event, and each juror's votes), `camps`, `moves` (with `cause`), `persuaders`, `challenges` (with `outcome` and `score`), `friction`, `holdouts`, `outcomes` (with `noAgreement`), `turnStructure`, `definitions` and `forepersonControlsVote: false`. `GET /api/matters/:matterId/deliberation/table?issueId=&baseRunId=&panelSize=` returns `{ matterId, simulated: true, label, runsRead, runsWithStrawPolls, filters, table }`, where `table.records` is exactly the `{ initialSplit, finalOutcome }` list that the forecast module's `estimateSchemeTable` takes, with `usable`, `excluded` (each with its reason), `finalSplits` and `transitions`; it holds counts only and names no juror.

## Case improvement plan (Strategy)

Open **Strategy**, then **Case improvement plan**. The plan shows where one party's case is weakest, proposes ways to cure the weaknesses, and lists a few non-obvious ideas. It is a model-generated draft; it is **not legal advice**, it is not a prediction, and the label "Model-generated draft; not legal advice" opens and closes every export. Live-model strategy quality has not been verified: the tests use a scripted model.

- **Choose a party.** The plaintiff is chosen first; any party of the case model can be chosen, so a defendant gets a plan from its own point of view. A plan is private to that party (a party-audience artifact). It never reaches a simulated juror or witness, and no plan changes a simulation, the evidence record, an admission ledger or the case model.
- **The weakness register is computed by code.** From signals the other screens approved: elements with no supporting evidence mapped (for the party that must prove them) or no contrary evidence (for the party that answers them), gaps the record states about itself, conflicts between accepted timeline events, vulnerabilities of experts the party retained (or whose retainer the report does not state, at a lower weight), open disclosure findings, simulated juror ballots and appraisals that went against the party in completed runs, and the party's own approved case summary's acknowledged weaknesses. Signals from the approved forecast, damages study, damages psychology study and style study join too, but only from an approved study that is still current: a draft, an unapproved or an out-of-date study gives nothing. A forecast signal restates the simulated figure with the sentence that it comes from simulated panels and has not been tested against real outcomes, and cites the stored study but no source passage, because a simulated figure is not evidence. A forecast signal is about a question the party bears or answers; damages and psychology signals go only to the party that claims the damages; a style study goes only to the party whose advocacy it styled and never appears in another party's plan. Findings about another party's expert are opportunities, not weaknesses, and are counted in a note.
- **Severity is calculated, never guessed.** `severity = round(100 × weight × lackOfSupport × dispute)`, each factor above 0 and at most 1 (weight: what rides on the point, such as a burden element 1, damages or a defence 0.8; lack of support: how little backs the party; dispute: how contested). 60 or more is high, 30 or more medium. Every row shows its three factors and cites what produced it: the stored item (artifact, finding, run or case model, with the version), the item inside it and the checked passages. A weakness with no signal, or whose cited passages all fail the source check, is rejected.
- **Cures.** For the most severe weaknesses (eight by default), one model call each proposes evidence to obtain, witness preparation, motions, pleading changes, expert retention or a settlement posture. Each states effort, risk and what would show it worked. A motion or pleading change cites an approved authority or is marked **Needs research**; a case, statute, rule or citation outside the approved list (the court rules' authorities and the curated instruction sections) is rejected.
- **Speculative ideas.** A separate call looks for non-obvious ideas. Each is badged **Speculative idea**, must cite passages found in the record, and then faces a separate adversarial critique. Code decides the result: a fatal objection refutes an idea whatever the critic's verdict says, and a critique that raised no objection tested nothing. Survivors show the objections that remain; the rest are listed under rejected. An idea that could not be critiqued is not shown.
- **What-ifs are labelled hypotheticals.** A cure or idea can carry a what-if scenario, shown as "Hypothetical — not evidence". It exists only inside the plan and cites nothing. Tests prove it never reaches the evidence tables, any admission ledger, the case model, or any juror or witness request.
- **Honest preparation only.** An instruction, a model output or a cure that proposes inventing or falsifying evidence, altering or destroying a record, false testimony, concealing evidence, or coaching a witness to say anything but the truth is refused by code and listed under "Refused by the honesty checks"; a refused instruction is refused before any model call and stays visible. Witness preparation must be framed as truthful preparation. These are pattern checks: they are a floor, a model can phrase an improper idea in words no pattern expects, and a lawyer must read every proposal.
- **Cost.** **Prepare a plan** shows a cost preview first: one call for each cured weakness, one for the ideas and at most one critique for each idea. Nothing is sent until you choose **Start preparing the plan**; the run stops at its cap and keeps what it finished.
- **Optional model check.** Off by default. Tick **Also check each claim with a model (costs more calls)** and each speculative idea that passed the code check is also put to a second model call that says whether the passages it cites support its stated reason, before its critique is paid for. An unsupported idea is rejected with its reason, an undecided one is badged **Not confirmed by model check**, and one that was not checked is badged **Not checked**. Cures cite no passage of their own, so they are not put to the check. The cost preview adds one checker call for up to five ideas. See Case summaries for how the check is worded, recorded and costed.
- **Approve, export, out of date.** Approving marks a version as reviewed by you. **Download Markdown** and **Download HTML** carry the labels, the signals with their citations, the what-ifs marked hypothetical and the refusals. A plan is marked out of date when a document, the court rules or an approved input (timeline, evidence index, expert assessment, case map, the party's summary) changes. Nothing regenerates for you.
- **Motion docket for any party.** `POST /api/case-models/:modelId/motions/draft` takes an optional `{ "movingPartyId": "..." }`. With none, the first accused, respondent or defendant moves, as before; a plaintiff can now move by being named.

API (under `/api/matters/:matterId/improvement-plan`, owner level): `POST /generate/preview` and `POST /generate` (body: optional `partyId`, `guidance`, `maxCures` 1-30, `maxIdeas` 0-8, `providerMode`, `externalDisclosureConfirmed`, `maxCalls`, `acknowledgeCost`; `/generate` also needs `estimateHash` from the preview), `GET /` (parties), `GET /:partyId`, `POST /:partyId/approve`, `GET /:partyId/export?which=draft|approved`. A dishonest `guidance` answers 422.

## Forecast: win rates and panel outcomes (Strategy)

**Strategy**, **Win rates and panel outcomes** runs a *study*: many seeded runs of the approved case model, one simulated panel at a time, and reports how often each side prevailed. Decision D1 was answered yes: the app shows a probability with its statistics. **Every screen, export and API answer carries the same label: the probabilities come from simulated panels and have not been tested against real outcomes, and there is no calibrated estimate in this build (calibration is milestone M9).** The label is built into the code and cannot be switched off. The votes of a single run are still not probabilities.

- **Setup and cost.** Choose the number of runs (1 to 500), screen or full mode, whether to record element findings (ballot contract v2, needed for the element table; off by default because live v2 behaviour is not verified) and, in full mode, witnesses. The preview shows model calls (runs times the per-run estimate the run screen uses, which counts a source check per stage, so it is a ceiling for a scripted run), tokens and the cap, before anything starts. A study over the default cap (`ANALYSIS_MAX_CALLS_PER_JOB`, 500, a placeholder for D6) needs an acknowledgement and a higher cap; no cap can pass 5,000 calls. Runs go through the job queue one at a time, never all at once, and are ordinary runs in the matter. A study that was interrupted, stopped at its cap or failed continues from where it stopped: finished runs are kept and never repeated (the same seed reuses them). A study whose estimate exactly fills its cap can end as `stopped_at_cap` although every run finished; its draft is still saved, and the screen asks for one run's worth of headroom.
- **Court rules.** The study uses the matter's chosen court rules for the panel size and decision rule. If none are chosen, or the panel size, decision rule or jury availability is unknown, the study is blocked with a plain-words reason; unknown is never read as six jurors or any rule. Only civil jury questions are forecast.
- **Liability table.** One row per defendant per claim: the probability that the party with the burden prevails (the share of simulated panels answering `proved`), n of N panels, a 95% Wilson interval over runs (runs, not jurors, are the sample), the hung share, and an **Exploratory** badge below 20 completed runs. A run with a missing or invalid ballot is left out of that question, with the reason, and is never counted as hung. Questions decided by the judge show no probability; damages and questions with no stated side are listed as not covered.
- **Elements** are the share of simulated jurors who found each element met. They are juror shares, never panel results unless the element is its own verdict question, and are never multiplied or combined into a claim probability.
- **Panel outcomes.** Exact math from the pooled juror share and the juror correlation (estimated from how much the share varies between runs; at least 10 runs, otherwise jurors are treated as independent and the screen says so), under the pinned rule; the deliberation table from initial split to final outcome with smoothing and four reference schemes (theory, not data); a sensitivity table for other panel sizes and rules (unanimous, a majority, one juror discharged) computed in code; the observed and modelled vote-split distribution as a table with bars that repeat the percentages in text; and, for two or more questions, the whole verdict form resampled juror by juror.
- **Saved results do not change.** The numbers, the wording and the manifest (run ids, court rules hash, jury profile hash, algorithm version `forecast-1`, study seed, provider and model) are stored in the artifact. A later code change never rewrites them. Everything random is seeded from the study seed, so recomputing from the stored runs gives the same hash. If the case model, admission ledger or court rules change, the forecast is shown as out of date and cannot be approved; nothing is recalculated.
- **Export** as Markdown or HTML (`GET .../forecast/export`); every dynamic string is collapsed to one line and escaped, and the label opens and closes the report.

**What is not verified.** Every test uses a scripted model. They prove the arithmetic, the pipeline, persistence, resumption, the cap and the screens, and that a scripted juror whose answer depends on a planted exhibit moves the result the right way. They do not show how a live model behaves, and nothing here is calibrated against real outcomes.

API (all under `/api/matters/:matterId/forecast`, owner level; every response has a `label` field): `POST /study/preview` with optional `runs`, `mode`, `seed`, `juryProfileHash`, `ballotContractV2`, `useWitnesses`, `providerMode`, `externalDisclosureConfirmed`, `maxCalls`, `acknowledgeCost` returns `{ label, params, plan: { blockers, panelSize, threshold, ruleText, juryQuestions, judgeQuestions, callsPerRun, existingRuns }, job }` where `job` is the job preview and `params` includes the seed; `POST /study` takes those `params` plus `estimateHash` (409 if the estimate changed or the plan has blockers) and returns 202 `{ label, job }`; `GET /` returns `{ label, current, draft?, approved? }` with views `{ artifact, content, freshness, label }`; `GET /versions` and `GET /versions/:artifactId`; `POST /approve`; `GET /export?which=draft|approved` returns `{ label, filename, generatedAt, markdown, html }`.

## Damages and caps, and jury psychology on damages (Strategy)

Two tabs in **Strategy**: **Damages and caps** (F12) and **Jury psychology on damages** (F13). Every screen, export and API answer carries a label saying the figures are simulated panel awards from a model playing jurors, not tested against real outcomes, not a valuation and not legal advice. The psychology label says the results are model behaviour, not human behaviour. **Live-model damages behaviour is not verified, nothing is calibrated, and the Ontario seed pack's caps, calculation order, interest, collateral benefits and damages categories are unknown until a reviewer enters them** (as a pack change or a recorded matter-level override through `PUT /api/matters/:id/framework`; the Court rules panel lists them but does not yet edit them).

- **Categories come from the court rules** (the new `damagesCategories` rule: a currency and categories of kind economic, non-economic, impairment, punitive or enrichment, with the local term as the label). Unknown means jurors cannot be asked and the study is blocked with that reason. A punitive category is asked and calculated only where `punitiveAvailability` is known true; otherwise it is left out and the reason is recorded in the run and the study.
- **Your inputs** are saved as versioned, hash-checked `damages_model` artifacts (subject `inputs`): low, likely and high claimed amounts per category with an optional cited passage (checked against the document on save; a failing passage stops the save), the claimant-fault assumption, policy limit, deductions, interest, liens, fee terms, collectability and assets, per-diem days and the defence's own counter-anchor figures. Money is typed in dollars and kept as whole cents; rates are whole basis points. A box left empty is **not entered**: it is never zero. "Does not apply" is a separate statement you make.
- **Juror amounts.** The run setting `damagesAmounts: true` (a checkbox under Deeper simulation; needs ballot contract v2, a civil jury run, court rules that state the categories, and a question that asks for money: answer type `amount`, or a damages question with no answer type of its own) makes every juror give an amount in each category, if the claim succeeded, in both ballot rounds. It adds no model calls. Missing, duplicated or foreign-currency amounts make that ballot invalid with the reason; nothing is completed for the juror. **Panel award = the median of the valid final juror amounts** (average of the middle two, rounded half to even; more than half the panel must count). The before-deliberation figure uses the initial ballots, and the difference is the severity shift. `GET /api/trials/:runId/damages` shows one run.
- **Study.** Seeded runs one at a time through the job queue under the hard cap (the cost preview equals the forecast's per-run figure). It reports per-category percentiles conditional on liability and across all simulated outcomes, a zero-inflated lognormal fit, the shift, and then the deterministic calculation **in the court rules' stated order**. If the order is unknown it says "Calculation order unknown" and shows only gross awards. A missing rule or input stops the calculation at that step, names what is missing and whether the court rules or you must supply it, and gives no net figure. Otherwise it shows a step-by-step ledger for the median scenario and gross and net-collectible percentiles over seeded resamples of whole panels. A cap is checked after every drawn calculation and is never exceeded. All arithmetic is integer cents with round-half-even and largest-remainder splitting. A percentage-stated cap is not applied (the rules do not say of what).
- **Saved studies are frozen** and pin the inputs (version and hash), the court rules hash, the jury profile hash, the seed, the algorithm version (`damages-1`) and the runs. Approve a draft to make it the study other features read; export as Markdown or HTML.
- **Psychology conditions** are run on common seeds in **full** runs (closing arguments exist only there): no number (baseline), low, central and high plaintiff anchors, a defence counter-anchor, per-diem and lump-sum framing, and fairness framing. The run setting `damagesCondition` adds a fixed, code-written paragraph to the closing argument; its figures are your claimed amounts (or explicit study parameters) formatted from cents, and a model never supplies a number. The court rules' `counselMaySuggestAmounts` decides availability (Ontario: Courts of Justice Act s. 118 is the starting point, shown with its scope for you to confirm); unknown or false makes every condition but the baseline unavailable, and the server refuses it with a readable reason (422) before anything is queued or run.
- **Results** use paired effects on common seeds with a seeded bootstrap: an effect is reported only when the 95% interval excludes zero, otherwise "no reliable effect" (direction null). Backfire is the highest anchor reliably producing lower awards than the one below it. The only grouping variable is the numeracy trait; no protected characteristic is a variable anywhere (a test scans the code and a saved result). Chapman and Bornstein (1996) and Diamond et al. (2011) are shown as a reference only. Fairness ratings are not measured.

API (owner level, under `/api/matters/:matterId`): `GET|PUT /damages/inputs`; `POST /damages/study/preview` and `POST /damages/study` (with the preview's `estimateHash`); `GET /damages`, `/damages/versions`, `/damages/versions/:artifactId`, `/damages/export`; `POST /damages/approve`; and the same under `/damages-psychology` plus `GET /damages-psychology/conditions`.

## Style studies (Strategy)

The **Style studies** tab in **Strategy** (F15) compares ways of delivering the same argument for ONE party on common seeds. Every screen, export and API answer says the results come from simulated panels (a language model playing advocates and jurors), have not been tested against real outcomes, are not a prediction of a real verdict and are not legal advice. **Live-model behaviour is not verified and nothing is calibrated.** This is preparation for your own side and is owner-only: the style chosen for a party is never given to the other side, the jurors or the judge of a simulated run.

- **A fixed catalogue, written by code** (`server/styles/catalogue.ts`, version `advocacy-styles-1`): moral appeal (bounded), pragmatic dealmaking, expert-driven logic, theatrical storytelling, plain and factual, and the length variants concise and thorough. Each is a short paragraph followed by the same guardrail: use only facts, figures, quotations and witness accounts in the admitted evidence you were given and cite them, state or imply nothing that is not in it, suggest nothing a witness should say, and rely on no protected characteristic. A style changes delivery only. **Custom styles (listed in the plan) are not built**: nobody can write a style, because a free-text style is a way to smuggle in an instruction to invent evidence, so the catalogue is closed. A test scans every text and fails if one mentions fabricating, coaching, concealing, overriding the rules, a protected characteristic or a figure, and checks that the scan itself can fail.
- **The run setting.** `advocacy: [{ partyId, id }]` on a run (a party and a catalogue id; a client cannot send text). The server pins the catalogue version and the exact text. The text is added to **that party's opening and closing argument requests only**, after the rest of the request, with the same source check and record. It is refused with a readable reason (400) for the courtroom protocol, a criminal or tribunal run, a judge-alone run, a run with no jury, a run with no court rules chosen (unknown is not a default), an unknown party or style, and a repeated party. The run records that a style was used in a non-public event for the owner (`advocacy_style_applied`, visible to `user` and the system only), never on a public event. A run with no style is byte-identical to one made before this existed (the golden regression, `tests/ballotCognitionRegression.test.ts`, holds it).
- **Study design.** Choose a party, the styles to compare, the number of common seeds (2 to 200), the mode (screen: openings only; full: openings, evidence and closings) and an optional seed. The study runs each seed once with no style (the baseline, always included) and once under each style, one run at a time through the job queue. The same simulated jurors meet every style. **Cost** = common seeds × (the baseline and every style) × the per-run estimate the run screen uses; a style adds no model calls. The preview shows the runs, the calls, the cap and the acknowledgement needed to raise it, and nothing runs until you start with that preview's estimate hash. This **replaces the old limit of 24 robustness variants for this study**: the job queue and its hard cap decide how much can run. The legacy robustness variants (`/trials/:runId/robustness`) still have their own limit of 24 and are unchanged. An interrupted or failed study keeps the runs that finished and resumes without repeating them.
- **Results** are computed by code (`server/forecast/styleEffects.ts`, seeded). Two measures from the styled party's side: the panel decision (the share of the questions the party can win or lose on which the panel went its way; a hung panel counts as not won) and the juror share (valid final ballots on the party's side). Each style is compared with the baseline on the same seeds: the paired difference with a seeded bootstrap interval, **controlled for argument length** (the outcome difference regressed on the paired length difference; the effect at equal length is what is judged, and the raw difference is shown beside it). A style that wins only by being longer is reported as no reliable difference, with a note that the effect came from length. The length control removes a straight-line effect only and needs lengths that differ from pair to pair; where they do not, the screen says length could not be separated. "Better" or "worse" is claimed only when the length-adjusted 95% interval excludes zero; otherwise "no reliable difference", which is a valid result and not a claim that the effect is zero. Fewer than 8 pairs gives "insufficient data"; fewer than 20 common seeds is marked exploratory. The recommendation uses the panel decision. Several styles are compared with the baseline separately and **not adjusted for multiple comparisons**, and the screen says so. The study records per-style run counts and mean argument length, example passages (model output, not evidence) and any run left out with its reason; a failed run is never counted as a loss.
- **Not built in this version:** phase-by-phase blends of styles, comparisons by element, by damages and by juror group, and styles for witness examinations. The results screen and export say so.
- **Saved studies are frozen** (`style_study` artifacts, owner audience): they pin the court rules hash, the jury profile hash, the case model version, the style catalogue version, the exact style texts, the seed, the algorithm version (`style-study-1`) and the runs. A draft is **out of date** when the approved case model, the court rules, the jury profile or the style catalogue has changed, and then it cannot be approved. Approve a draft to record that a person reviewed it; export as Markdown or HTML (every dynamic string is collapsed to one line, so model text cannot start a heading or list item, and the label opens and closes the report).

API (owner level, under `/api/matters/:matterId/style-studies`): `GET /styles` (the catalogue with exact texts, the parties and any blockers); `POST /study/preview` and `POST /study` (202, with the preview's `estimateHash`); `GET /`, `/versions`, `/versions/:artifactId`, `/export`; `POST /approve`.

## Archives, Recovery, and Database Upgrades

Matter archives use the versioned `judge-jury-matter` JSON format. Version 5 is written only when a matter has chosen court rules. Version 4 is written when a matter has saved analysis artifacts but no chosen court rules. Version 3 is used for matters containing `courtroom_v1` runs and includes courtroom state, command receipts and original serialized actor requests; legacy-only matters continue exporting version 2. All preserve source blobs by SHA-256, corpus manifests, derived OCR/transcripts, approved case models, theories, disclosure findings, motions/rulings, admission ledgers, trial events, actor snapshots, ballots, decision sheets, and provider audit metadata. Import verifies the archive checksum and every blob hash, creates collision-safe IDs, and rewrites current internal references while retaining execution provenance. Version 1 imports remain supported and receive empty v2 workflow collections; unsupported future versions fail closed.

- `GET /api/matters/:matterId/archive` exports a matter archive.
- `POST /api/matters/import` imports a matter archive.
- `POST /api/system/backup` creates a consistent SQLite backup under `data/backups/` using SQLite's online backup API.

Database changes are applied transactionally and tracked with SQLite `PRAGMA user_version`, currently 12 (v3 corpus, v4 case/motion/admission workflow, v5 event engine, v6 courtroom records, v7 evidence scopes, v8 preview hashes, v9 private evidence notes, v10 analysis artifacts, v11 analysis jobs, v12 court rules). Keep `data/judge-jury.sqlite`, `data/evidence/`, and `data/corpus/blobs/` together during manual recovery. See [Recovery and archive compatibility](recovery-and-archives.md).

## Local and Remote API Safety

The default `HOST=127.0.0.1` mode is loopback-only and does not require authentication. A non-loopback `HOST` fails at startup unless `LOCAL_API_TOKEN` contains at least 24 characters and `ALLOWED_ORIGINS` contains explicit comma-separated origins. In remote mode every API and SSE request requires `Authorization: Bearer <LOCAL_API_TOKEN>`. Requests are rate-limited in memory; configure the per-client ceiling with `API_RATE_LIMIT_PER_MINUTE`.

The built-in browser client is intended for loopback mode. Put remote deployments behind a TLS reverse proxy that injects the bearer token and does not log it.

TrialForge authorities are a curated local registry, not a live citator. The UI exposes provenance and source notes, unknown model-generated IDs are suppressed, and `npm run check:authorities` checks whether curated source links remain reachable without claiming substantive legal validation.

## Verification

```powershell
npm run lint
npm run typecheck
npm test
npm run build
npm run test:ui
npm run test:sim
npm run test:arguments
npm run check:authorities
```

The Playwright smoke test starts the local API and Vite client, verifies the empty no-demo workspace, exercises TrialForge exhibit and authority drill-downs, completes and reopens a saved rehearsal, and checks that only Local and External provider modes are exposed. It does not run a live model simulation unless a real provider is configured separately.

`npm run test:sim` runs a full simulation end to end against a scripted OpenAI-compatible provider (no real model needed): it verifies the realistic stage order, the twelve independent secret-ballot calls, per-stage sampling temperatures, hung-jury calibration, and the exported report.

`npm run test:arguments` exercises the Full Proceeding browser workflow with the [fictional Crown and defence packet](../samples/criminal-fraud/README.md), editable parties/counts/source coverage, versioned document-use restrictions, separate private theories, disclosure review, a judicial-instructions checkpoint, twelve initial and final ballots, archive export, three robustness variants, and restored decisions after reload. It uses deterministic injected actors and an isolated temporary database. Reports, screenshots, and the fictional archive are saved in `tmp/qa/arguments/`. UI defects make this command exit with status 1. This regression test does not assess live model quality or validate legal conclusions; private live-case tests use separate ignored artifacts.
